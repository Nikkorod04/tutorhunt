============================================================
1. PROJECT OVERVIEW
============================================================

Tutor Hunt is a mobile application designed for tutors and parents.

The application has two major purposes:

1. Tutor Management
   Tutors can manage their students, tutoring sessions, expenses, payments,
   reimbursements, earnings, and parent statements.

2. Tutor Marketplace
   Parents can browse available tutors and post tutoring requests.
   Tutors can browse parent requests and publish their own public tutor profile.

The system should initially focus on Tacloban City but must be structured so
other cities and municipalities can be added later.

The application should prioritize:
- simplicity
- low Firebase usage
- low operating cost
- mobile-first UX
- secure private student data
- clear separation between private tutor data and public marketplace data
- freemium monetization
- expandable architecture

6. SUBSCRIPTION / ENTITLEMENT DESIGN
============================================================

Each tutor account has a separate entitlement document.

Entitlements must NOT live in users/{uid}. The user document is owner-writable
(see 31), so any entitlement stored there can be granted by the client itself.

Entitlement document:

entitlements/{uid}

{
  "uid": "firebase auth uid",
  "plan": "free",
  "proUntil": null,
  "trialEndsAt": null,
  "usageMonth": "2026-10",
  "pdfStatementsThisMonth": 1,
  "updatedAt": timestamp
}

Write policy, enforced by Firestore rules (see 31):
- the owner may CREATE this document only with plan == "free" and proUntil == null
- the owner may UPDATE only usageMonth and pdfStatementsThisMonth
- pdfStatementsThisMonth may increase by at most 1 per update
- plan, proUntil and trialEndsAt are immutable from the client
- Pro activation happens through the Admin SDK, the Firebase console or a
  future Cloud Function (see 33) — never from the mobile client

activeStudentCount is deliberately NOT stored. It is derived on demand
(see 7.3).

IMPORTANT:
Do not query the database every time a premium feature is tapped.

Recommended flow:

App launch/login
-> fetch users/{uid} and entitlements/{uid} once
-> store entitlement in Zustand/Auth state
-> use cached plan information in the UI
-> refresh only when necessary
-> re-read after any action that consumes quota, such as generating a PDF

Plan constants should be centralized.

Example:

PLAN_LIMITS = {
  free: {
    maxStudents: 2,
    monthlyPDFs: 2,
    recurringSessions: false,
    reimbursementTracking: false,
    advancedAnalytics: false
  },

  pro: {
    maxStudents: Infinity,
    monthlyPDFs: Infinity,
    recurringSessions: true,
    reimbursementTracking: true,
    advancedAnalytics: true
  }
}

Do not hard-code plan limits across multiple screens.

============================================================
7. FIREBASE USAGE MINIMIZATION RULES
============================================================

The agent must follow these rules.

7.1 Avoid unnecessary realtime listeners

Do NOT attach onSnapshot listeners to:
- all students
- all sessions
- all expenses
- all marketplace tutors
- all parent posts

Use standard reads when a screen opens.

Realtime listeners should only be used where they provide real value.

7.2 Paginate large collections

Never load an entire lifetime of sessions.

Example:
- load most recent 10 sessions
- load more on demand

Marketplace:
- load 10 to 20 tutor profiles
- paginate
- load 10 to 20 parent posts
- paginate

7.3 Derive the active student count, do not store it

CHANGED IN v1.1. v1.0 stored an activeStudentCount counter and updated it on
every activate/archive/restore. That counter lived in an owner-writable
document, so a client could edit it, and it drifted whenever a write failed or
happened offline.

Instead, derive the count at the moment of use with a bounded query:

  where("status", "==", "active"), limit(maxActiveStudents + 1)

For a Free tutor the limit is 2, so this is at most 3 document reads — cheaper
than maintaining a counter, and it cannot drift.

Rules:
- never store a derived count in Firestore
- if a bounded query is ever too slow, move the counter behind a trusted
  backend, never into a client-writable document

7.4 Keep public marketplace documents small

Public tutor cards should contain only data required for listings.

Load additional details only when user opens tutor profile.

7.5 Store images in Firebase Storage

Never store Base64 image data in Firestore.

Firestore stores URLs only.

7.6 Generate PDFs locally

Do not upload every generated statement unless a future feature requires it.

7.7 Cache loaded account/plan state

Use Zustand or Context.

7.8 Use built-in student avatars

Default avatars:
- boy
- girl
- neutral/custom future option

Only upload to Firebase Storage if custom avatar is selected.

============================================================
13. SESSION RULES
============================================================

Automatically calculate:

durationMinutes =
(endsAt - startsAt) in minutes

If hourly:
sessionFee =
(durationMinutes / 60) * appliedRate

If per-session:
sessionFee =
appliedRate

BILLABLE (v1.1)
Default by status:
- completed               -> billable = true
- student_absent          -> billable = false, tutor may set true
- cancelled_by_parent     -> billable = false, tutor may set true
- cancelled_by_tutor      -> billable = false
- scheduled / rescheduled -> billable = false

A session produces a charge when:

  status == "completed" OR billable == true

This lets a tutor charge for a no-show or a late cancellation without forcing
that policy on every tutor. billable may only be set true on a completed,
student_absent or cancelled_by_parent session.

Cancelled sessions must remain in history for attendance tracking even when
they are not billable.

A session with status "rescheduled" must point at its replacement through
rescheduledToId. The replacement is an ordinary session; the original stays in
history and is not billable unless the tutor says otherwise.

14. RECURRING SESSIONS
============================================================

Pro feature.

Example:
Tuesday and Thursday
4:00 PM to 5:30 PM
October 10 to December 15

Recommended implementation (revised in v1.1):
Create individual session documents for the generated dates, AND one template
document so the series can be managed as a unit.

users/{tutorUid}/recurringSeries/{seriesId}

{
  id: string,
  studentId: string,
  weekdays: number[],
  startDate: timestamp,
  endDate: timestamp,
  startTime: string,
  endTime: string,
  subject: string,
  topicCategory: string,
  skipDates: [timestamp],
  generatedSessionIds: [string],
  status: "active" | "ended" | "cancelled",
  createdAt: timestamp,
  updatedAt: timestamp
}

Each generated session keeps recurringGroupId == seriesId, so the link resolves
in both directions.

Series-level operations the tutor must be able to perform:
- extend the end date and generate only the additional sessions
- edit the series, applied to future unmodified sessions only
- cancel the series, removing the remaining future sessions in one action

Guards:
- cap a series at 100 sessions or 6 months, whichever comes first
- never regenerate a date that already has a session in the series
- skipDates exists so Philippine holidays can be excluded
- editing or cancelling a series must never touch a session that is already
  completed or billable

Do not build highly complex calendar recurrence rules for MVP.

Support:
- selected weekdays
- start date
- end date
- start time
- end time
- subject
- topic
- student

Example:

AMOUNT SEMANTICS (v1.1)
amount was ambiguous: the example above implies PHP 40 per date, but a single
scalar field could equally be read as PHP 40 in total. The field is therefore
renamed amountPerOccurrence, meaning:

  expense total = amountPerOccurrence * expenseDates.length

The example above is PHP 120 in total, not PHP 40.

REIMBURSEMENT LIFECYCLE (v1.1)
- not_requested          -> set when the expense is created
- included_in_statement  -> set when a statement containing it is generated;
                            statementId is recorded at the same time
- paid                   -> set by the tutor when the parent pays

An expense moves forward through these states only. Generating another
statement must never re-flag an expense that is already included_in_statement
or paid.

If querying expenses by individual date becomes important later,
migrate to expense occurrences.

SOURCE OF TRUTH (v1.1)
The payments collection is the single source of truth for money received.
Outstanding is computed per student:

  charges(student) = sum of billable session fees for that student
                   + sum of reimbursable expense totals for that student
  outstanding(student) = charges(student) - sum(payments for that student)

There is no per-session allocation in the MVP. A payment is recorded against a
student, not against particular sessions. This keeps the ledger unambiguous and
matches how tutors actually collect money.

If per-session paid status is ever required, derive it for display by applying
payments to sessions oldest-first, and never write the result back to the
session document.

============================================================
17. EARNINGS
============================================================

Tutor dashboard should calculate:

- total completed-session fees
- total amount paid
- outstanding balance
- reimbursable expenses
- reimbursed expenses
- non-reimbursable tutor expenses
- net tutoring income

Suggested formulas (v1.1):

Gross Session Earnings =
sum(sessionFee for sessions where status == "completed" OR billable == true)

Reimbursable Expense Total =
sum(amountPerOccurrence * expenseDates.length for reimbursable expenses)

Outstanding (per student) =
billable session fees + reimbursable expense totals - payments received
for that student

Outstanding (dashboard) =
sum of Outstanding(per student) across all students

Tutor Costs =
sum of non-reimbursable expense totals

Net Tutor Income =
payments received - tutor costs

BASIS NOTE (v1.1)
Gross Session Earnings and Outstanding are accrual figures: they count what was
earned or charged, whether or not cash arrived. Net Tutor Income is a cash
figure: it counts money actually received. The two are not comparable, and the
dashboard must label them so a tutor does not read Net as "earnings".

DATE BASIS (v1.1)
- session charges fall on startsAt
- expense charges fall on the earliest entry in expenseDates
- payments fall on datePaid
All month and range filtering must use these fields.

Do not create unnecessary aggregate documents in MVP unless performance requires it.

Use date-range queries when needed.

19. PDF USAGE TRACKING
============================================================

Use fields in the entitlement document (see 6), not the user document:

entitlements/{uid}
  usageMonth: "YYYY-MM"
  pdfStatementsThisMonth: number

When current month changes:
reset counter to zero when user next generates a PDF.

Example logic:

if usageMonth != currentMonth:
  usageMonth = currentMonth
  pdfStatementsThisMonth = 0

Then check plan limit.

ENFORCEMENT (v1.1)
The client may update these two fields and nothing else, and
pdfStatementsThisMonth may increase by at most 1 per update (see 31). That
closes the v1.0 hole where a client could write 0 and reset its own quota.

TIMEZONE (v1.1)
currentMonth is computed in Asia/Manila (UTC+8), not from the raw device clock.
If the device clock disagrees with the server, the server value wins.

the tutor but NOT writable by the tutor. The security rules pin those four
fields so a client update cannot change them (see 31). They are set only by an
admin or a trusted backend. A tutor must never be able to award itself a
verification badge.

============================================================
25. MARKETPLACE SEARCH / FILTERS
============================================================

FIRESTORE CONSTRAINTS (v1.1)
v1.0 listed subject, grade level, area, mode and rate as independent filters.
Firestore cannot execute that: a query allows at most ONE array-contains, and a
range over two fields (minRate and maxRate) is not expressible at all. The
filter set must be defined against what the database can actually do.

Queryable tutor filters:
- subject        -> array-contains on subjects (the only array filter)
- city           -> equality on city
- tutoring mode  -> equality on primaryMode
- grade band     -> equality on gradeBand
- minimum rate   -> range on rateFrom (<=)
- verified       -> equality on credentialsVerified

Every tutor query:
  where city == selected
  where isVisible == true
  [+ at most one array-contains, or one equality, or one range]
  order by updatedAt desc
  limit 15
  startAfter(cursor)

DEFAULT SORT (v1.1)
Tutors are ordered by updatedAt descending. Every paginated list needs a stable
order, or startAfter returns duplicates and gaps. v1.0 never stated one.

Queryable parent post filters:
- subject        -> array-contains on a subjects array on the post
- city           -> equality on city
- tutoring mode  -> equality on tutoringMode
- grade level    -> equality on gradeLevel
- status         -> equality on status
Ordered by createdAt desc.

Do NOT build complex full-text search initially.

MVP search must not attempt:
- more than one array-contains per query
- free-text matching on shortBio or description
- sorting by rating (reviews are post-MVP, so every rating is empty)

If full-text search becomes necessary later:
consider a dedicated search provider.

REQUIRED COMPOSITE INDEXES (v1.1)
firestore.indexes.json must contain at least:
- tutorProfiles: city ASC, isVisible ASC, updatedAt DESC
- tutorProfiles: city ASC, isVisible ASC, primaryMode ASC, updatedAt DESC
- tutorProfiles: city ASC, isVisible ASC, gradeBand ASC, updatedAt DESC
- tutorProfiles: city ASC, isVisible ASC, rateFrom ASC, updatedAt DESC
- tutorProfiles: subjects ARRAY, city ASC, isVisible ASC, updatedAt DESC
- parentPosts: status ASC, createdAt DESC
- parentPosts: status ASC, city ASC, createdAt DESC
- sessions: studentId ASC, startsAt DESC
- sessions: status ASC, startsAt ASC
- expenses: reimbursable ASC, expenseDates ARRAY

31. FIREBASE SECURITY CONCEPT
============================================================

Private user data must only be accessible by the owner.

REVISED IN v1.1. v1.0 stated "users/{uid} allow read/write only if
request.auth.uid == uid" while also storing plan, proUntil and the usage
counters in that same document, so the client could grant itself Pro. The rules
below close that and the other gaps found in review.

Concept:

users/{uid}
- read: owner only
- create: owner only, and role must be one of tutor/parent/admin
- update: owner only, but role and accountStatus must be unchanged
- delete: denied; account deletion runs through a trusted backend (see 33)

users/{uid}/students/*, sessions/*, expenses/*, payments/*, progressNotes/*,
statements/*, recurringSeries/*, favorites/*
- read/write: owner only
- additionally denied when the owner's accountStatus == "suspended"

entitlements/{uid}
- read: owner only
- create: owner only, and plan must be "free" and proUntil must be null
- update: owner may change only usageMonth and pdfStatementsThisMonth, and
  pdfStatementsThisMonth may increase by at most 1
- plan, proUntil, trialEndsAt: never writable by the client

tutorProfiles/{uid}
- read: signed-in users
- create/update: matching uid only
- rating, reviewCount, identityVerified, credentialsVerified: must be unchanged
  on any client update (pinned fields)

parentProfiles/{uid}
- read: the owner always; other signed-in users only when contactVisible == true
- write: matching uid only

parentPosts/{postId}
- read: signed-in users
- write: the creating parent only

reports/{reportId}
- create: signed-in users
- read/update: admin only, via a custom claim

SUSPENSION (v1.1)
accountStatus is now actually enforced. A suspended account can still sign in
and read its own data, but every write under its own subtree is denied.

ADMIN (v1.1)
Admin access uses a Firebase Auth custom claim (admin == true), set only through
the Admin SDK. It is never read from a Firestore document, because a Firestore
document is exactly what a client could edit.

IMPORTANT:
Do not rely only on screen hiding for security.

============================================================

MVP (revised in v1.1):

41. DATE/TIME RULES
============================================================

Use timestamps for actual dates.

Sessions store startsAt and endsAt as real Firestore Timestamps (changed in
v1.1; v1.0 stored free-text time strings, which cannot be ordered or compared).

TIMEZONE (v1.1)
The app operates in Asia/Manila (UTC+8). Firestore Timestamps are UTC, so:
- convert to local time only for display
- compute "today" and month boundaries as [local midnight, next local midnight)
  converted to UTC before querying
- never compare a local date string against a stored Timestamp

Display using Philippine-friendly formatting.

Recommended display:
Oct 7, 2026
4:00 PM

Store dates in a way compatible with Firestore Timestamp.

Avoid relying only on formatted strings for dates.

============================================================

AUTHORITY (v1.2)
The full visual language is specified in DESIGN_PLAN.md, which is the source of
truth for colour, typography, spacing, radius, elevation, motion, component
variants and interaction states. This section states the intent; the design plan
states the implementation. Do not invent colours, spacing or durations outside
the design plan's tokens.

Design should feel:
- friendly
- educational
- modern
- lightweight
- trustworthy

Avoid:
- overly corporate interface
- crowded dashboards
- decorative animation
- excessive Firebase-backed refreshes
- raw hex values or arbitrary spacing inside a screen
- pure black or all-white large surfaces

Use:
- cards
- clear status chips with an icon and a label, never colour alone
- clear currency formatting
- simple forms
- good empty states with an illustration and an action
- obvious Save buttons
- loading indicators
- skeletons only if useful
- purposeful motion: press feedback, list entrance, sheet springs, animated
  money counters
- one dominant primary action per screen

MOTION LINE (v1.2)
v1.0 said "avoid unnecessary animations". That is now the purposeful-versus-
gratuitous rule in section 6 of DESIGN_PLAN.md. Motion that explains a change is
required; motion that decorates is banned. That section carries the explicit
allow list and the banned list.

54. AGENT DEVELOPMENT RULES
============================================================

When using an AI coding agent, follow these instructions:

1. Read this entire blueprint before modifying code.

2. Build only the current requested phase.

3. Do not implement future features unless required for architecture.

4. Do not replace the selected stack without permission.

5. Use Expo SDK 57 compatible libraries only.

6. The project must continue to run in Expo Go unless a future explicitly
   approved feature requires a development build.

7. Use TypeScript.

8. Keep Firebase reads/writes minimal.

9. Do not use realtime listeners by default.

10. Paginate Firestore list queries, with a fixed documented order.

11. Do not duplicate Firestore data unless there is a clear read optimization.

12. Never store images as Base64 in Firestore.

13. Do not create one massive component.

14. Separate:
    - UI
    - services
    - state
    - utilities
    - types

15. Keep plan limits centralized.

16. Never trust premium status solely from client UI.

17. Never delete user data because a plan expired.

18. Maintain backwards-compatible database fields where possible.

19. Before installing a package:
    - confirm Expo SDK 57 compatibility
    - explain why it is required
    - avoid unnecessary dependencies

20. After each phase:
    - run TypeScript checks
    - check navigation
    - test CRUD
    - verify Firebase paths
    - verify Security Rules assumptions
    - summarize changed files

21. Never store a derived count. Derive it with a bounded query.

22. Never place an entitlement, quota counter or verification flag in a document
    the client can write.

23. Keep utils/pricing.ts pure and covered by tests. All money maths goes
    through it; no screen computes fees, totals or balances on its own.

24. Any new query must be reflected in firestore.indexes.json, and any new
    collection must be reflected in firestore.rules.

25. Never hardcode a colour, spacing, radius, elevation or duration in a screen
    or component. Use the theme tokens in theme/ as specified in
    DESIGN_PLAN.md.

v1.0 to v1.1 — ARCHITECTURE
------------------------------------------------------------

This revision was produced from a full review of v1.0. Every change is listed
with the section it affects. Nothing was removed without a replacement.

SECURITY AND ENTITLEMENTS

- 6  Entitlements moved out of users/{uid} into a new entitlements/{uid}
     document. v1.0 stored plan and proUntil in an owner-writable document, so
     the client could grant itself Pro. The client may now create the document
     only as "free", may update only the two usage fields, and can never change
     plan, proUntil or trialEndsAt.
- 7.3 The stored activeStudentCount counter was removed. It was client-writable
     and drift-prone. The count is now derived with a bounded query.
- 9  plan, proUntil, trialEndsAt, usageMonth, pdfStatementsThisMonth and
     activeStudentCount removed from the user document. role is now immutable.
- 19 PDF quota tracking moved to entitlements/{uid}, with a rule that the
     counter may increase by at most 1 per update, and an Asia/Manila month
     boundary. v1.0 let a client write 0 and reset its own quota.
- 20 rating, reviewCount, identityVerified and credentialsVerified are now
     pinned fields: readable by the tutor, not writable by the tutor.
- 31 The security concept was rewritten with explicit rules. Added: role and
     accountStatus immutability, suspension enforcement, entitlement rules,
     pinned verification fields, parentProfiles read gating, and admin access
     via a custom claim rather than a Firestore document.
- 32 Subscription security aligned with the entitlements document.
- 33 Manual Pro activation is now explicitly an Admin SDK / console action.
- 8  subscriptions/{uid} was declared but never modelled. Replaced by
     entitlements/{uid}.

MONEY AND DATA MODEL

- 12 Session startTime and endTime were free-text strings; replaced by startsAt
     and endsAt Timestamps. sessionDate removed. amountPaid and paymentStatus
     removed from sessions. billable added. rescheduledToId added.
- 13 Billable rules added: completed sessions bill by default, and a tutor may
     mark a no-show or late cancellation as billable. v1.0 left cancelled and
     absent sessions undefined.
- 15 expense.amount renamed to amountPerOccurrence and its meaning fixed as
     per-date, so the PHP 40 / Oct 2, 4, 6 example is PHP 120 in total.
     statementId added and the reimbursement lifecycle defined.
- 16 The payments collection is now stated to be the single source of truth,
     with outstanding computed per student and no per-session allocation.
     v1.0 stored payment state in two places with no rule for which won.
- 17 Earnings formulas rewritten to use billable sessions and
     amountPerOccurrence, with an accrual-versus-cash basis note and an explicit
     date basis per figure.

MARKETPLACE

- 22 parentProfiles gained contactVisible, default false, and a read rule.
- 23 parentPosts gained contactVisible. Post contact is read from the parent
     profile, never duplicated onto the post.
- 24 Favorites now carry a small display snapshot. v1.0 forced one profile read
     per favourite just to render the list.
- 25 The filter list was rewritten against Firestore's real limits: at most one
