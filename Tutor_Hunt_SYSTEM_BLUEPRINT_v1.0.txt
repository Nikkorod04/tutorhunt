============================================================
1. PROJECT OVERVIEW
============================================================

Tutor Hunt is a mobile application designed for tutors and parents.

The application has two major purposes:

1. Tutor Management
   Tutors can manage their students, tutoring sessions, expenses, payments,
   reimbursements, earnings, and parent statements.

2. Tutor Marketplace
   Parents can browse available tutors and post tutoring requests.
   Tutors can browse parent requests and publish their own public tutor profile.

The system should initially focus on Tacloban City but must be structured so
other cities and municipalities can be added later.

The application should prioritize:
- simplicity
- low Firebase usage
- low operating cost
- mobile-first UX
- secure private student data
- clear separation between private tutor data and public marketplace data
- freemium monetization
- expandable architecture

============================================================
2. MAIN USER ROLES
============================================================

2.1 TUTOR

A tutor can:
- register/login
- create and edit a tutor account
- manage students/tutees
- record tutoring sessions
- create recurring tutoring sessions
- track tutoring expenses
- mark expenses as reimbursable by parents
- track payments and unpaid balances
- view earnings summaries
- generate PDF statements
- create a public tutor profile
- browse parent tutor-request posts
- contact parents through allowed external contact methods
- manage subscription/freemium access

2.2 PARENT

A parent can:
- register/login
- browse tutor profiles
- filter tutors
- view tutor details
- save/favorite tutors
- post "Looking for Tutor" requests
- edit/delete own posts
- contact tutors using available external contact methods
- report suspicious/inappropriate tutor profiles or posts

2.3 ADMIN

Admin features are not required for the earliest MVP but the database should
support an admin role.

Future admin responsibilities:
- review reports
- review tutor verification requests
- suspend abusive accounts
- manage marketplace content
- manually activate subscriptions if needed
- review credentials
- manage supported locations/categories

Recommended flow:

-> fetch current user account once
-> store entitlement in Zustand/Auth state

  }
}

Do not hard-code plan limits across multiple screens.

============================================================
7. FIREBASE USAGE MINIMIZATION RULES
============================================================

The agent must follow these rules.

7.1 Avoid unnecessary realtime listeners

Do NOT attach onSnapshot listeners to:
- all students
- all sessions
- all expenses
- all marketplace tutors
- all parent posts

Use standard reads when a screen opens.

Realtime listeners should only be used where they provide real value.

7.2 Paginate large collections

Never load an entire lifetime of sessions.

Example:
- load most recent 10 sessions
- load more on demand

Marketplace:
- load 10 to 20 tutor profiles
- paginate
- load 10 to 20 parent posts
- paginate

7.3 Store counters

Do not count student documents every time.

Store:
activeStudentCount

Update counter when:
- student is activated
- student is archived
- student is restored

7.4 Keep public marketplace documents small

Public tutor cards should contain only data required for listings.

Load additional details only when user opens tutor profile.

7.5 Store images in Firebase Storage

Never store Base64 image data in Firestore.

Firestore stores URLs only.

7.6 Generate PDFs locally

Do not upload every generated statement unless a future feature requires it.

7.7 Cache loaded account/plan state

Use Zustand or Context.

7.8 Use built-in student avatars

Default avatars:
- boy
- girl
- neutral/custom future option

Only upload to Firebase Storage if custom avatar is selected.

13. SESSION RULES
============================================================

Automatically calculate:

durationMinutes =
end time - start time

If hourly:
sessionFee =
(durationMinutes / 60) * appliedRate

If per-session:
sessionFee =
appliedRate

Only completed sessions should count toward completed-session earnings.

Cancelled sessions should remain in history for attendance tracking.

17. EARNINGS
============================================================

Tutor dashboard should calculate:

- total completed-session fees
- total amount paid
- outstanding balance
- reimbursable expenses
- reimbursed expenses
- non-reimbursable tutor expenses
- net tutoring income

Suggested formulas:

Gross Session Earnings =
sum(sessionFee for completed sessions)

Outstanding =
session charges + reimbursable expenses - payments received

Tutor Costs =
sum(non-reimbursable expenses)

Net Tutor Income =
payments received - tutor costs

Do not create unnecessary aggregate documents in MVP unless performance requires it.

Use date-range queries when needed.

51. FIRESTORE QUERY EXAMPLES
============================================================

Recent sessions:
- where studentId == selectedStudent
- order by sessionDate desc
- limit 10

Tutor marketplace:
- where city == "Tacloban City"
- where isVisible == true
- limit 15

Parent requests:
- where status == "open"
- order by createdAt desc
- limit 15

Expenses:
- order by latest relevant date
- limit 20

Use startAfter for pagination.

52. DATA PRIVACY PRINCIPLES
============================================================

Because tutors may store information about children:

- collect only necessary data
- keep student information private
- never expose students in marketplace
- do not make birthday publicly visible
- secure Firebase rules
- avoid storing unnecessary sensitive information
- allow tutor to delete/archive records
- do not expose parent details publicly unless intentionally published

Custom student photos should be optional.

Built-in avatars should be encouraged.

54. AGENT DEVELOPMENT RULES
============================================================

When using an AI coding agent, follow these instructions:

1. Read this entire blueprint before modifying code.

2. Build only the current requested phase.

3. Do not implement future features unless required for architecture.

4. Do not replace the selected stack without permission.

5. Use Expo SDK 57 compatible libraries only.

6. The project must continue to run in Expo Go unless a future explicitly
   approved feature requires a development build.

7. Use TypeScript.

8. Keep Firebase reads/writes minimal.

9. Do not use realtime listeners by default.

10. Paginate Firestore list queries.

11. Do not duplicate Firestore data unless there is a clear read optimization.

12. Never store images as Base64 in Firestore.

13. Do not create one massive component.

14. Separate:
    - UI
    - services
    - state
    - utilities
    - types

15. Keep plan limits centralized.

16. Never trust premium status solely from client UI.

17. Never delete user data because a plan expired.

18. Maintain backwards-compatible database fields where possible.

19. Before installing a package:
    - confirm Expo SDK 57 compatibility
    - explain why it is required
    - avoid unnecessary dependencies

20. After each phase:
    - run TypeScript checks
    - check navigation
    - test CRUD
    - verify Firebase paths
    - verify Security Rules assumptions
    - summarize changed files
